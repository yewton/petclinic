# PetClinic プロダクトバックログ

## プロダクトの到達像

PetClinic は、小規模な伴侶動物病院が、飼い主との最初の予約相談から診療後の継続ケアまでを、一貫して引き継げるようにするプロダクトである。

```text
飼い主の相談・予約
  → 受付の確認・日程調整
  → 来院・待機・診療への引継ぎ
  → 診療・説明・処方／次回対応
  → 請求・支払状態
  → 診療要約の共有
  → 再診・予防・慢性ケアのフォロー
```

最終 To-Be は [`to-be-architecture/`](to-be-architecture/) に LikeC4 として定義する。PetClinic は、病院が導入・運用する一つの Software System として表す。その内部で、院内業務、飼い主ポータル、飼い主向け公開 API、同意・通知、診療所データを Container 境界として分ける。診療・請求の正本は Clinic Care Database が保持し、飼い主向けの Container は Owner Care API を介して公開済みの情報だけを扱う。具体的な Web 技術は To-Be に固定しない。

このバックログは完成形から逆算したプロダクトバックログである。現在の `tasks.md` は、この全体像のうち最初に実装・検証する縦切りだけを表す。

## 初期の縦切り

完成形を一度に実装しない。最初のリリースは各役割が実際に判断できる結果を残す、次の小さな縦切りで進める。

1. 受付が既存の飼い主・ペットについて電話予約依頼を記録し、選択日の一覧で確認できる。
2. 受付が来院を記録し、獣医師が待機中の患者を診療へ引き継げる。
3. 獣医師が次の対応・再診日・飼い主向け要約を記録し、受付が期限リストで追える。
4. 受付が要約を印刷し、診療後の金額と支払状態を記録できる。
5. これらの業務をレビューした後、本人確認を伴う飼い主ポータルの最初の機能として、予約状況と確定済み要約の閲覧を提供する。

各縦切りの Definition of Done には、親子関係の検証、既存 `Visit` の保持、入力検証、必要な日時・操作主体の記録、WebTestClient による正常系と越境更新のテストを含める。これらは独立した先行機能ではなく、届ける業務価値を安全に成立させる品質条件として扱う。

## 今回の変更との対応

`add-clinic-care-workflow` は、上記のエピック 1〜4 にある最初の四つの縦切りを検証する変更である。飼い主ポータル、認証、通知、決済・会計・検査の外部連携は、プロダクトの最終像に含むが、この実装変更には含めない。
